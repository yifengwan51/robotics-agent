\section{Problem Diagnosis and Audit Scope}
\label{sec:diagnosis}

\noindent\textbf{Held-out development split.}
EB-Navigation's five test subsets (Base, Common-sense, Complex, Visual-appearance, Long-horizon) use 60 iTHOR
rooms. The project contains a development split built with the benchmark's own generator and instruction files on
30 unused rooms (150 episodes; disjoint from the test rooms by construction). The reported formal result
directories use the full official test set (300 episodes). We retain this split distinction because it is the
intended model-selection protocol, while separately documenting that later component comparisons revisit test data.

\noindent\textbf{Audit boundary.}
This section separates what the saved artifacts establish from what they do not. The runner records one JSON
file per episode, including success, step count, planner-call statistics, and any runner exception. It also logs
analysis-only target distance and visibility, but these values are never passed to S2M or the EB-prompt planner.
The artifact audit cannot retroactively prove that every configuration choice was made only on development data;
moreover, the test set has subsequently been used for several one-run component checks. We consequently treat
the component table as diagnostic evidence and reserve claims about final model selection for an independent split.

\noindent\textbf{Recognition probe.}
For every official test episode we render the start view and the three other 90$^\circ$ headings, and ask the
VLM (i) whether the target is visible (the yes/no first-token probability) and (ii) for its bounding box. We then
score against the simulator's instance boxes, which are used only for evaluation. The raw probe outputs are retained
under \texttt{runs/grounding/}.  We preserve a simple, directly traceable IoU$\geq0.3$ hit/visible aggregation in
\cref{app:dev-history}, but treat it as an auxiliary recognition diagnostic rather than as navigation evidence:
candidate-verification records still lack a checked aggregate.

\noindent\textbf{Oracle ceilings.}
Given the true target position, our diagnostic geometric planner (\cref{sec:method}) succeeds in 93.3\% on Base,
83.3\% on Long-horizon, and 91.3\% overall on the official 300-episode test set using the depth-built map. This is
an oracle-target diagnostic, not a deployable planner, and is not compared causally with the VLM baselines.

\noindent\textbf{Appearance-only goals are recall-limited.}
The Visual subset is consistently lower than the other S2M subsets in the saved main runs (50.0--56.7\% versus
80.0--91.7\% in the named-object subsets). A targeted candidate-recall analysis remains pending. The auxiliary
probe is consistent with lower start-view grounding on Visual, but it is not a causal failure attribution for an
interactive navigation episode.

\noindent\textbf{Failure taxonomy.}
Detailed error-taxonomy percentages are intentionally omitted: the analysis script exists, but no saved,
cross-checked aggregate taxonomy is present in the result artifacts.

\noindent\textbf{Baseline output validity.}
The Qwen3 EB-prompt run contains no recorded JSON decoding errors. In contrast, Qwen2.5 EB-prompt records 768
decode failures across 255/300 episodes. The benchmark parser substitutes a random action after a decode failure,
so the 5.7\% number blends model planning failures with output-format failures. This motivates the parser caveat
in \cref{tab:main}; a parser-instrumented rerun is needed before treating that row as a model comparison.

\noindent\textbf{Implication for the method.}
These observations motivate a narrow design goal rather than a claim that small VLMs cannot plan: preserve only
the VLM decisions that are grounded in the current image, and make spatial memory, consistency checks, and action
selection explicit. The next section specifies this controller. Its experimental comparison must nevertheless be
read with the sensing and parser caveats above.
